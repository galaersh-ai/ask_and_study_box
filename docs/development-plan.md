# План разработки Knowledge Box

**Версия:** 0.1

**Дата:** 13 сентября 2026 г.

**Статус:** план для согласования; разработка не начата

## 1. Цель и граница

MVP — локально разворачиваемая платформа, которая принимает готовый предметный
пакет и материалы, формирует версионную базу знаний, выполняет гибридный поиск
и отвечает на вопросы с точными цитатами.

В MVP входят:

- проекты и импорт готовых предметных пакетов;
- загрузка, нормализация и версионирование источников;
- извлечение сущностей, фактов, связей и Evidence;
- экспертная проверка спорных результатов;
- полнотекстовый, векторный и, при доказанной пользе, графовый поиск;
- Q&A с привязкой утверждений к цитатам и версиям;
- API, MCP, минимальный Web UI, задания, аудит и эксплуатационные функции;
- демонстрационные пакеты «Синтетическая компания» и «Курс по AI-агентам».

За границами MVP:

- встроенная студия проектирования предметной области;
- Learning Studio и генерация учебных курсов;
- Assessment, прохождение тестов и адаптивное обучение;
- юридический корпус и юридическая логика;
- интернет-ingest и автономное «забывание»;
- микросервисное разбиение без подтверждённой эксплуатационной причины.

## 2. Архитектурная стратегия

Предлагается модульный монолит с гексагональными границами. Это предложение,
а не подтверждённый выбор стека; оно должно быть закреплено ADR на PH-00.

```text
Web UI / CLI / API / MCP
          │
  use cases модулей
          │
┌─────────┴────────────────────────────────────────────┐
│ projects │ sources │ knowledge (Knowledge Core)     │
│ review   │ retrieval │ q_and_a │ jobs │ access      │
│ audit    │ exports                                      │
└─────────┬────────────────────────────────────────────┘
          │ ports
┌─────────┴────────────────────────────────────────────┐
│ storage │ parsers │ embeddings │ llm │ search │ cache│

```

## 3. Карта модулей

| ID | Модуль | Ответственность | Минимальные тесты |
|---|---|---|---|
| MOD-01 | `shared` | Идентификаторы, ошибки, время, версии, общие типы | unit; property для идентификаторов и версий |
| MOD-02 | `projects` | Жизненный цикл проекта и импорт предметного пакета | unit; contract схемы пакета; acceptance импорта |
| MOD-03 | `sources` | Реестр источников, версии, checksum, парсинг и чанки | unit; contract парсеров; integration хранилища |
| MOD-04 | `knowledge` | DomainSchema, Entity, Fact, Relation, Evidence, snapshot | unit; property инвариантов; integration репозитория |
| MOD-05 | `review` | Очередь проверки и ReviewDecision | unit переходов; integration аудита |
| MOD-06 | `retrieval` | Индексы, кандидаты, слияние и ранжирование | unit формул; contract индексов; quality-набор |
| MOD-07 | `q_and_a` | План ответа, claims, citations, отказ при нехватке Evidence | unit; prompt contract; acceptance «вопрос → источник» |
| MOD-08 | `jobs` | Идемпотентные фоновые задания, повтор, остановка, отчёт | unit state machine; integration очереди |
| MOD-09 | `access` | Проекты, роли и политики доступа | unit матрицы; negative integration tests |
| MOD-10 | `audit` | Неизменяемые события действий и происхождения результата | unit; integration; проверка полноты lineage |
| MOD-11 | `exports` | Выгрузка проекта, ответа, evidence и версий | contract формата; round-trip integration |
| MOD-12 | `interfaces` | API, MCP, CLI и минимальный Web UI без бизнес-логики | contract API/MCP; integration; smoke UI |
| MOD-13 | `adapters` | БД, FTS, vector/graph, LLM, embeddings, parsers, cache | contract на каждый порт; offline fixtures |
| MOD-14 | `domain_packages` | Два независимых демо-пакета | schema tests; acceptance общего цикла |

Зависимости направлены внутрь: интерфейсы и адаптеры зависят от публичных
контрактов модулей, доменные модули не зависят от адаптеров. Точный граф
импортов фиксируется на PH-00 и проверяется `import-linter`.

## 4. Этапы

### PH-00. Основание и решения

Результат: пустой, но запускаемый каркас разработки без бизнес-функций.

- утвердить архитектурный стиль и Python-стек;
- оформить ADR модульного монолита, хранилищ, гибридного поиска и LLM-портов;
- создать пакеты `src/` и зеркальные каталоги unit-тестов;
- зафиксировать зависимости в `uv.lock`;
- включить lint, format, types, import boundaries, tests, coverage и
  `detect-secrets` с проверенным baseline;
- создать CI с тем же набором команд, что и локально;
- уточнить существующий baseline требований и связать ID с модулями, тестами
  и критериями приёмки;
- подготовить черновые C1/C2/C3 и граф разрешённых импортов;
- принять шаблон спецификации модуля: контракт, зависимости, алгоритм, тесты,
  «готово, когда».

Готово, когда чистый клон одной командой создаёт окружение, все проверки зелёные,
а в репозитории нет прикладной логики.

### PH-01. Контракты проекта и предметного пакета

Зависит от PH-00. Результат: два минимальных пакета проходят одну схему
валидации, но ещё не загружают документы.

- Project, DomainPackage manifest, DomainSchema и версии;
- glossary, aliases, validation rules, questions и sources manifest;
- проверка совместимости и понятные диагностические ошибки.

Готово, когда новый пакет можно проверить без изменения ядра и без сети.

### PH-02. Источники и версии

Зависит от PH-01. Результат: материал проходит путь «файл → нормализованный
документ → версия → разделы → координаты».

- реестр источников, checksum и дедупликация;
- адаптеры разрешённых форматов;
- повторная загрузка, новая версия и неизменяемый исходник;
- безопасные лимиты размера и типа файла.

Готово, когда повторный ingest идемпотентен, а цитату можно однозначно вернуть
к версии и координатам исходника.

### PH-03. Knowledge Core, Evidence и review

Зависит от PH-02. Результат: проверяемый snapshot знаний.

- Entity, Fact, Relation и Evidence;
- порты LLM/embeddings и offline-заглушки;
- валидация структурированного ответа модели;
- очередь проверки и аудит решения;
- версия промпта и модели в lineage.

Готово, когда неподтверждённая цитата отклоняется, а решение эксперта
воспроизводимо и аудируется.

### PH-04. Retrieval и измерительный spike

Зависит от PH-03. Результат: измеренная стратегия поиска.

- эталонный набор вопросов для двух демо-пакетов;
- полнотекстовый baseline;
- векторный поиск;
- слияние, фильтры доступа и ранжирование;
- отдельный графовый вариант только для сравнения.

Готово, когда ADR-005 и ADR-008 приняты по метрикам качества, задержки,
сложности и ресурсов. Граф не включается по умолчанию без доказанного выигрыша.

### PH-05. Q&A с цитированием

Зависит от PH-04. Результат: первый сквозной сценарий MVP.

- retrieval plan и контекстный бюджет;
- структурированный ответ: claims, citations, confidence, limitations;
- проверка цитат и отказ при недостатке Evidence;
- защита от prompt injection в документах;
- кэш с ключом по snapshot, запросу, промпту, модели и настройкам.

Готово, когда каждый существенный claim имеет валидную цитату либо система
явно сообщает, что данных недостаточно.

### PH-06. Управление, интерфейсы и аудит

Зависит от PH-05. Результат: управляемый локальный сервис.

- задания, остановка, повтор и восстановление;
- API и MCP на одном application layer;
- роли и доступ на уровне проекта;
- аудит, health/readiness, резервное копирование и экспорт.

Готово, когда API и MCP проходят общие контрактные тесты, а перезапуск не теряет
состояние завершённых и прерванных заданий.

### PH-07. Демо и минимальный Web UI

Зависит от PH-06. Результат: два честных демонстрационных сценария.

- импорт каждого пакета без правки кода;
- загрузка, поиск, вопрос, цитата, просмотр источника и версии;
- экран состояния заданий и очереди review;
- сценарии демонстрации и ограничения продукта.

Готово, когда обе предметные области проходят один acceptance-сценарий,
а интерфейс не обещает Learning Studio, Assessment или юридическую точность.

### PH-08. Переносимость и эксплуатационная приёмка

Зависит от PH-07. Результат: проверенный путь внешняя LLM → локальная LLM.

- capability profile провайдера;
- проверка качества на целевом оборудовании;
- установка, обновление, backup/restore и offline replay;
- безопасность секретов, зависимостей и локального контура;
- актуализация C1/C2/C3, runtime и deployment views по реализованной системе.

Готово, когда развёртывание повторяемо, восстановление проверено, а различия
провайдеров измерены на одном наборе.

## 5. После MVP

1. Learning Studio читает только зафиксированный `KnowledgeSnapshot` и создаёт
   конспекты, карточки и мини-курсы как производные артефакты.
2. Assessment хранит критерии, Evidence, попытки и результаты; ошибка модели
   возвращает `needs_review`, а не условный балл.
3. Юридический пакет создаётся отдельным проектом через те же контракты. Он не
   добавляет юридическую логику в Knowledge Core.
4. Встроенная студия предметной области рассматривается после нескольких
   пилотов и анализа реального процесса настройки.

## 6. Решения и открытые вопросы

Подтверждено концепцией:

- граница MVP;
- два демо-пакета;
- схема создаётся вне MVP;
- внешняя LLM допустима в runtime при переносимости на локальную модель;
- evidence, версии, аудит и модульность обязательны;
- Knowledge Core отделён от Q&A, Learning Studio и Assessment.

Требует решения до соответствующего этапа:

- конкретные СУБД, FTS и векторное хранилище;
- необходимость графового хранилища;
- формат Web UI;
- очередь заданий и модель процессов;
- минимальная матрица ролей;
- поддерживаемые форматы документов и предельные размеры;
- измеримые пороги качества retrieval и Q&A;
- характеристики целевого оборудования для локальной модели.
