# План разработки Knowledge Box

**Версия:** 0.6

**Дата:** 14 сентября 2026 г.

**Статус:** план для согласования; разработка не начата

## 1. Цель и граница

MVP — локально разворачиваемая платформа, которая принимает готовый предметный
пакет и материалы, формирует версионную базу знаний, выполняет гибридный поиск
и отвечает на вопросы по фактам с точными цитатами. Пользователи — автор
и читатели.

В MVP входят:

- проекты, роли «автор» и «читатель», импорт готовых предметных пакетов;
- загрузка PDF, DOCX, Markdown, XLSX и CSV, нормализация, версионирование
  и ручное удаление ошибочно загруженных документов;
- извлечение сущностей, фактов, связей и Evidence;
- проверка спорных результатов автором;
- полнотекстовый, векторный и, при доказанной пользе, графовый поиск;
- Q&A по фактам с привязкой утверждений к цитатам и версиям;
- API, MCP, CLI, минимальный Web UI, задания, аудит и эксплуатационные функции;
- демонстрационные пакеты «Синтетическая компания» и «Курс по AI-агентам»;
- русский язык документов, ответов и интерфейса.

Вторая очередь сразу после MVP — Learning Studio (раздел 5, ADR-010).

Третья очередь после Learning Studio — Assessment. Его предварительные этапы
PH-13–PH-15 и точка решения описаны в разделе 6.

За границами MVP, Learning Studio и Assessment:

- адаптивное обучение и учёт прогресса — следующая очередь после Assessment;
- встроенная студия проектирования предметной области;
- юридический корпус и юридическая логика;
- интернет-ingest и автономное «забывание»;
- микросервисное разбиение без подтверждённой эксплуатационной причины.

## 2. Архитектурная стратегия

Предлагается модульный монолит с гексагональными границами. Это предложение,
а не подтверждённый выбор стека; оно должно быть закреплено ADR на PH-00.

```text
Web UI / CLI / API / MCP
          │
  use cases модулей
          │
┌─────────┴────────────────────────────────────────────┐
│ сценарные модули: learning │ assessment              │
├──────────────────────────────────────────────────────┤
│ projects │ sources │ knowledge (Knowledge Core)     │
│ review   │ retrieval │ q_and_a │ jobs │ access      │
│ audit    │ exports                                      │
└─────────┬────────────────────────────────────────────┘
          │ ports
┌─────────┴────────────────────────────────────────────┐
│ storage │ parsers │ embeddings │ llm │ search │ cache│
└──────────────────────────────────────────────────────┘
```

Сценарные модули зависят от публичных контрактов ядра, ядро от них не зависит.

## 3. Карта модулей

| ID | Модуль | Ответственность | Минимальные тесты |
|---|---|---|---|
| MOD-01 | `shared` | Идентификаторы, ошибки, время, версии, общие типы | unit; property для идентификаторов и версий |
| MOD-02 | `projects` | Жизненный цикл проекта и импорт предметного пакета | unit; contract схемы пакета; acceptance импорта |
| MOD-03 | `sources` | Реестр источников, версии, checksum, парсинг, чанки, удаление | unit; contract парсеров; integration хранилища |
| MOD-04 | `knowledge` | DomainSchema, Entity, Fact, Relation, Evidence, snapshot и события его изменения | unit; property инвариантов; contract snapshot; integration репозитория |
| MOD-05 | `review` | Очередь проверки и ReviewDecision | unit переходов; integration аудита |
| MOD-06 | `retrieval` | Индексы, кандидаты, слияние и ранжирование | unit формул; contract индексов; quality-набор |
| MOD-07 | `q_and_a` | План ответа по фактам, claims, citations, отказ при нехватке Evidence | unit; prompt contract; acceptance «вопрос → факт → источник» |
| MOD-08 | `jobs` | Идемпотентные фоновые задания, повтор, остановка, отчёт | unit state machine; integration очереди |
| MOD-09 | `access` | Проекты, роли «автор» и «читатель», политики доступа | unit матрицы; negative integration tests |
| MOD-10 | `audit` | Неизменяемые события действий и происхождения результата | unit; integration; проверка полноты lineage |
| MOD-11 | `exports` | Выгрузка проекта, ответа, evidence и версий | contract формата; round-trip integration |
| MOD-12 | `interfaces` | API, MCP, CLI и минимальный Web UI без бизнес-логики | contract API/MCP; integration; smoke UI |
| MOD-13 | `adapters` | БД, FTS, vector/graph, LLM, embeddings, parsers, cache | contract на каждый порт; offline fixtures |
| MOD-14 | `domain_packages` | Два независимых демо-пакета | schema tests; acceptance общего цикла |
| MOD-15 | `learning` | Вторая очередь: учебные материалы, их версии и публикация | unit; contract чтения snapshot; prompt contract; acceptance AC-L |
| MOD-16 | `assessment` | Предлагаемая третья очередь: задания, рубрики, попытки и результаты | unit модели попытки; contract способов проверки; acceptance AC-A |

Зависимости направлены внутрь: интерфейсы, адаптеры и сценарные модули зависят
от публичных контрактов ядра, доменные модули не зависят от адаптеров и
сценарных модулей. Точный граф импортов фиксируется на PH-00 и проверяется
`import-linter`.

Модули MOD-08–MOD-10 появляются раньше полной реализации: их контракт и
минимальная реализация нужны этапам, которые на них опираются. Полная
реализация — на PH-06.

## 4. Этапы MVP

### PH-00. Основание и решения

Результат: пустой, но запускаемый каркас разработки без бизнес-функций.

- утвердить архитектурный стиль и Python-стек;
- оформить ADR модульного монолита, гибридного поиска и LLM-портов;
- принять часть ADR-008 о базовом хранилище (метаданные, файлы, полнотекстовый
  поиск) с явными границами: число проектов, документов на проект, объём хранилища,
  одновременные пользователи, задержка ответа. Исходная оценка из NFR-009:
  100–200 документов на стартовый проект и файл до 50 МБ по умолчанию. Это
  номинально до 10 ГБ исходников при максимальном числе файлов, но не верхняя
  граница хранилища: ADR-008 отдельно учитывает версии, производные данные,
  индексы и резервные копии;
- для расчётов взять подтверждённый baseline: 50 МБ по умолчанию и 100–200
  документов на стартовый проект. Дополнительные рабочие предположения,
  не являющиеся требованиями: жёсткий предел 100 МБ, до 20 ГБ исходников
  с версиями и до 50 ГБ рабочих данных проекта без backup; предупреждение
  при 80% квоты, запрет нового ingest при 95% с сохранением чтения; не более
  двух ingest-заданий на проект. Для неизвестного оборудования предлагается
  два задания на установку по умолчанию; четыре — только верхний сценарий
  проверки «два активных проекта × два задания», который должен подтвердить
  benchmark PH-00;
- создать пакеты `src/` и зеркальные каталоги unit-тестов;
- зафиксировать зависимости в `uv.lock`;
- включить lint, format, types, import boundaries, tests, coverage и
  `detect-secrets` с проверенным baseline; утвердить порог покрытия;
- создать CI с тем же набором команд, что и локально;
- принять ADR-010 или зафиксировать альтернативную границу сценарных модулей,
  затем отразить её в графе импортов;
- связать ID требований с модулями, тестами и критериями приёмки;
- подготовить черновые C1/C2/C3 и граф разрешённых импортов;
- принять шаблон спецификации модуля: контракт, зависимости, алгоритм, тесты,
  «готово, когда».

Готово, когда чистый клон одной командой создаёт окружение, все проверки зелёные,
а в репозитории нет прикладной логики.

### PH-01. Проект, роли и предметный пакет

Зависит от PH-00. Результат: два пакета проходят одну схему валидации, роли
описаны контрактом, документы ещё не загружаются.

- Project, DomainPackage manifest, DomainSchema и версии;
- glossary, aliases, validation rules, questions и sources manifest;
- контракт `access`: роли «автор» и «читатель», допуск к проекту;
- наполнение обоих демо-пакетов исходными материалами, чтобы на PH-04 было
  на чём строить эталонный набор;
- проверка совместимости и понятные диагностические ошибки.

Готово, когда новый пакет можно проверить без изменения ядра и без сети,
а проверка доступа покрыта unit-тестами матрицы ролей.

### PH-02. Источники, версии и удаление

Зависит от PH-01. Результат: материал проходит путь «файл → нормализованный
документ → версия → разделы → координаты» и может быть удалён.

- реестр источников, checksum и дедупликация;
- адаптеры PDF, DOCX, Markdown, XLSX и CSV;
- единый контракт стабильных локаторов с представлением для каждого формата:
  страница/область PDF, раздел/абзац/ячейка DOCX, заголовок/блок Markdown,
  лист/ячейка или диапазон XLSX, строка/столбец CSV;
- повторная загрузка, новая версия и неизменяемый исходник;
- лимиты типа и размера файла из настроек, по умолчанию 50 МБ, в границах
  неизменяемого верхнего предела установки и квоты проекта из ADR-008;
- минимальные задания `jobs`: запуск, состояние, повтор для ingest;
- после принятия ADR-011 — удаление документа со всеми версиями и событие
  «документ удалён».

Готово, когда повторный ingest идемпотентен, цитату можно однозначно вернуть
к версии и координатам исходника, а результат удаления соответствует принятому
ADR-011 и проверяется его критериями.

### PH-03. Knowledge Core, Evidence и review

Зависит от PH-02. Результат: проверяемый snapshot знаний и первый сквозной
минимум.

- Entity, Fact, Relation и Evidence;
- `KnowledgeSnapshot` как версионный результат Knowledge Core для
  воспроизводимости (NFR-002); публичный контракт и события изменения снимка
  добавляются только после принятия ADR-010;
- порты LLM/embeddings и offline-заглушки; извлечение фактов через задания;
- валидация структурированного ответа модели;
- критерии спорного результата (FR-005) и очередь проверки автором;
- минимальный аудит решений review; аудит удаления — по принятому ADR-011;
- отзыв фактов, у которых после удаления не осталось Evidence,
  по принятому ADR-011;
- версия промпта и модели в lineage;
- сквозной минимум в CLI: полнотекстовый поиск по фактам → ответ-заглушка
  с цитатой до фрагмента исходника.

Готово, когда неподтверждённая цитата отклоняется, решение автора
воспроизводимо и аудируется, а сквозной минимум проходит на одном демо-пакете.

### PH-04. Retrieval и измерительный spike

Зависит от PH-03. Результат: измеренная стратегия поиска.

- эталонный набор вопросов для двух демо-пакетов: готовит агент, проверяет
  человек;
- полнотекстовый baseline;
- векторный поиск;
- слияние, ранжирование и фильтр доступа по контракту `access` до retrieval;
- обработка записей удалённого документа в индексах по принятому ADR-011;
- отдельный графовый вариант только для сравнения.

Готово, когда ADR-005 и векторно-графовая часть ADR-008 приняты по метрикам
качества, задержки, сложности и ресурсов. Граф не включается по умолчанию без
доказанного выигрыша.

### PH-05. Q&A по фактам с цитированием

Зависит от PH-04. Результат: первый полный сквозной сценарий MVP.

- retrieval plan и контекстный бюджет;
- ответ строится по фактам: claims, ссылки на Fact и Evidence, confidence,
  limitations;
- проверка цитат и отказ при недостатке Evidence;
- защита от prompt injection в документах;
- кэш с ключом по snapshot, запросу, промпту, модели и настройкам; очистка кэша
  при удалении документа — по принятому ADR-011.

Готово, когда каждый существенный claim ссылается на факт с валидной цитатой
либо система явно сообщает, что данных недостаточно.

### PH-06. Управление, интерфейсы и аудит

Зависит от PH-05. Результат: управляемый локальный сервис. Этап разбит на три
части, каждая — отдельный PR.

**PH-06.1. Задания.** Остановка, повтор и восстановление после перезапуска;
задания принимают долгие операции любого модуля.
Готово, когда перезапуск не теряет состояние завершённых и прерванных заданий.

**PH-06.2. API, MCP и CLI.** Один application layer для всех трёх интерфейсов.
Готово, когда API и MCP проходят общие контрактные тесты.

**PH-06.3. Доступ, аудит и экспорт.** Полная матрица ролей, аудит всех действий,
документированный формат экспорта снимка и ответа, health/readiness, резервное
копирование.
Готово, когда negative-тесты доступа (AC-010) и round-trip экспорта проходят.

### PH-07. Демо и минимальный Web UI

Зависит от PH-06. Результат: два честных демонстрационных сценария.

- импорт каждого пакета без правки кода;
- экраны автора: загрузка, удаление, задания, очередь review;
- экраны читателя: вопрос, ответ, цитата, просмотр источника и версии;
- сценарии демонстрации и ограничения продукта.

Готово, когда обе предметные области проходят один acceptance-сценарий,
а интерфейс не обещает Learning Studio, Assessment или юридическую точность.

### PH-08. Переносимость и эксплуатационная приёмка

Зависит от PH-07. Результат: проверенный путь облачного инференса к локальному.

- capability profile провайдера;
- выбор целевого оборудования и проверка качества на нём;
- установка, обновление, backup/restore и offline replay;
- безопасность секретов, зависимостей и локального контура;
- актуализация C1/C2/C3, runtime и deployment views по реализованной системе.

Готово, когда развёртывание повторяемо, восстановление проверено, а различия
провайдеров измерены на одном наборе. После приёмки PH-08 начинается вторая
очередь.

## 5. Вторая очередь: Learning Studio

Требования — [`requirements/learning-studio-baseline.md`](requirements/learning-studio-baseline.md),
предлагаемое решение — ADR-010. Начинается после приёмки PH-08. До принятия
ADR-010 его обязательства по контрактам ядра не считаются утверждёнными.

### PH-09. Контракт учебных материалов

Зависит от PH-08. Результат: модуль `learning` подключён без изменения ядра.

- утвердить требования второй очереди и проверить актуальность принятого
  на PH-00 решения о границе сценарных модулей; изменение оформить новым ADR;
- модель данных: учебный материал, версия, публикация;
- контракт версионного `LearningPackage`: цели, структура, содержание,
  практика, представление, медиа, Evidence, отчёт проверок и форматы поставки;
- чтение `KnowledgeSnapshot` и подписка на события изменения снимка;
- промпты `prompts/learning/` с контрактными тестами;
- eval-набор материалов: готовит агент, проверяет человек.

Готово, когда `import-linter` подтверждает отсутствие зависимостей ядра от
`learning`, а контракт чтения снимка покрыт тестами.

### PH-10. Генерация и проверка материалов

Зависит от PH-09. Результат: автор получает проверяемые черновики.

- предварительная сборка полного `LearningPackage`: конспекты, карточки,
  структура мини-курса, сценарии сцен, задания, медиа и экспорты;
- ссылка каждого утверждения на Fact и Evidence, отказ от утверждений без них;
- генерация фоновым заданием;
- проверка, правка и отклонение автором с аудитом;
- пометка устаревших материалов при новой версии документа или снимка.

Готово, когда AC-L-002, AC-L-006 и первая часть AC-L-003 проходят.

### PH-11. Вопросы для самопроверки без оценивания

Зависит от PH-10. Результат: материал содержит самостоятельную проверку без
перехода к Assessment.

- вопрос, эталонный ответ, пояснение и Evidence входят в `LearningPackage`;
- автор проверяет вопрос и ответ до публикации;
- читатель открывает эталонный ответ после самостоятельного размышления;
- система не принимает ответ на оценивание и не создаёт баллы, попытки,
  результаты или записи прогресса;
- contract и acceptance tests подтверждают отсутствие зависимости от будущего
  модуля Assessment и записей его данных.

Готово, когда AC-L-007 проходит, а в данных и аудите нет сущностей попытки,
балла, результата или прогресса.

### PH-12. Публикация читателям и демо

Зависит от PH-11. Результат: сценарий второй очереди на пакете «Курс по
AI-агентам».

- публикация, доступ читателя только к опубликованному;
- выдача сохранённого пакета без генерации обязательного содержимого по запросу
  читателя;
- API, MCP и экраны Web UI для материалов;
- снятие с публикации при удалении документа (ADR-011);
- экспорт материала в Markdown.

Готово, когда AC-L-001…AC-L-007 проходят.

## 6. Третья очередь: Assessment

Assessment включён в план после Learning Studio. Требования — предварительный
[`requirements/assessment-baseline.md`](requirements/assessment-baseline.md),
граница — proposed ADR-012. Детали не утверждены; этапы PH-14–PH-15 можно
изменить по решению владельца на PH-13.

### PH-13. Требования и точка архитектурного решения

Зависит от PH-12. Результат: принято решение, достаточно ли включать Assessment
и в каком составе продолжать. До результата этого этапа прикладной код MOD-16
не создаётся.

- подтвердить или отменить очередь Assessment;
- согласовать типы заданий, назначение, шкалу, повторные попытки и порог;
- определить автоматическую, LLM- и экспертную проверку;
- определить `needs_review`, права автора и читателя;
- определить сроки хранения, удаление, экспорт и видимость результатов;
- утвердить требования Assessment и принять, отклонить или заменить ADR-012;
- подтвердить или перепланировать PH-14–PH-15.

Готово, когда владелец явно утвердил дальнейший объём и критерии. Отсутствие
решения завершает очередь без реализации, а не разрешает значения по умолчанию.

### PH-14. Задания, попытки и проверка — предварительно

Зависит от принятого решения PH-13. Предлагаемый результат: отдельный MOD-16
хранит версионные задания, рубрики, попытки, ответы и результаты.

- контракты AssessmentItem, Rubric, Attempt, Answer и EvaluationResult;
- ссылки вопросов и объяснений на Fact и Evidence;
- детерминированные правила проверки и утверждённый порт LLM-проверки;
- `needs_review` при неоднозначности или технической ошибке без условного балла;
- unit, contract, integration и negative tests для каждой выбранной стратегии.

Готово, когда принятые на PH-13 критерии проходят без зависимости Knowledge
Core и Learning Studio от MOD-16.

### PH-15. Проверка автором, результаты и демо — предварительно

Зависит от PH-14. Предлагаемый результат: автор проверяет спорные результаты,
а читатель видит собственный подтверждённый результат.

- очередь `needs_review` и версионное решение автора;
- аудит происхождения результата и экспорт в утверждённом формате;
- проверки доступа и сроков хранения;
- сквозной сценарий на учебном демо-пакете;
- отсутствие создания попыток при самопроверке PH-11;
- acceptance tests утверждённого baseline Assessment.

Готово, когда все принятые AC-A проходят. Агрегированный прогресс,
адаптивная траектория и рекомендации следующих материалов не входят в этап.

### Последующие очереди

1. **Адаптивное обучение и учёт прогресса.** Траектория читателя, отчёты
   автору. Опирается на данные Assessment.
2. **Юридический пакет.** Отдельный проект через те же контракты, без юридической
   логики в Knowledge Core.
3. **Студия предметной области.** После нескольких пилотов и анализа реального
   процесса настройки.

## 7. Решения и открытые вопросы

Подтверждено концепцией:

- граница MVP;
- два демо-пакета;
- схема создаётся вне MVP;
- evidence, версии, аудит и модульность обязательны;
- Knowledge Core отделён от Q&A, Learning Studio и Assessment.

Подтверждено владельцем 14 сентября 2026 г.:

- Learning Studio — вторая очередь сразу после MVP;
- Assessment включён третьей очередью после Learning Studio, но его состав
  утверждается отдельным решением на PH-13 до реализации PH-14;
- адаптивное обучение и учёт прогресса — следующие очереди;
- пользователи — автор и читатели; автор — создатель и администратор проекта, не только учебного курса;
- форматы PDF, DOCX, Markdown и таблицы, файл до 50 МБ как значение по умолчанию;
- расчётная нагрузка: 100–200 документов на стартовый проект, немного
  одновременных читателей;
- Q&A строится по фактам с указанием использованных фрагментов текста;
- автор может удалить ошибочно загруженный документ;
- только русский язык;
- эталонный набор готовит агент, проверяет человек;
- в MVP используется облачный инференс модели, допускающей локальное развёртывание.

Требует решения до соответствующего этапа:

- конкретные СУБД, FTS и границы нагрузки — PH-00;
- неизменяемый верхний предел размера файла и квота проекта — PH-00;
- контракт стабильных локаторов для каждого формата — до PH-02;
- векторное хранилище и необходимость графа — PH-04;
- критерии спорного результата — до PH-03;
- формат Web UI — до PH-07;
- очередь заданий и модель процессов — PH-02;
- измеримые пороги качества retrieval и Q&A — PH-04;
- целевое оборудование для локальной модели — до PH-08;
- срок хранения резервных копий с удалёнными документами — PH-06.3;
- состав мини-курса и пороги качества материалов — до PH-09.
- требования, граница, оценивание и хранение Assessment — PH-13.
