# Правила разработки Knowledge Box

**Версия:** 0.1

**Статус:** предлагаются к утверждению вместе с планом

## 1. Источники истины

Приоритет документов:

1. действующие требования в `docs/requirements/`;
2. принятые ADR в `docs/architecture/decisions/`;
3. публичные контракты модулей;
4. план разработки;
5. код и тесты;
6. комментарии и обсуждения.

Код не может молча отменить требование или ADR. Архивные версии помещаются
в `archive/`, явно помечаются и не используются как основание для изменений.

## 2. Спецификация модуля

До кода для каждого модуля создаётся раздел или отдельный действующий документ:

- назначение и граница ответственности;
- публичные входы, выходы и ошибки;
- владельцы данных;
- разрешённые зависимости и порты;
- алгоритм и инварианты;
- настройки и версии;
- угрозы и отказные сценарии;
- unit, contract, integration и acceptance tests;
- миграция и совместимость, если применимо;
- наблюдаемость;
- «готово, когда».

Модуль без тестов и условия готовности не считается завершённым.

## 3. Тестовая стратегия

| Уровень | Что проверяет | Правило |
|---|---|---|
| Unit | Доменные правила и чистые преобразования | Быстро, детерминированно, без I/O |
| Contract | Все реализации одного порта | Один набор тестов для stub/local/cloud |
| Integration | База, индекс, файловое хранилище, очередь | Изолированная временная среда |
| Acceptance | Пользовательский сценарий по демо-пакету | Проверяемый результат и цитата |
| Quality/Eval | Retrieval и LLM-поведение | Версионный набор, метрики и пороги |
| Security | Доступ, инъекции, файлы, секреты | Негативные сценарии обязательны |

Общие требования:

- внешняя сеть в обычных тестах заблокирована;
- ответы провайдеров находятся в `tests/fixtures/` и не содержат секретов;
- реальная модель используется только в явно помеченном eval-профиле;
- время, UUID и случайность внедряются и фиксируются в тестах;
- изменение промпта запускает его contract и quality tests;
- исправление дефекта содержит тест, воспроизводящий дефект;
- coverage используется как барьер регрессии, но не заменяет проверку поведения;
- порог покрытия утверждается на PH-00 и затем не понижается без ADR.

## 4. Конфигурация и секреты

Предлагаемый порядок наложения настроек:

```text
config/defaults.yaml
→ config/<environment>.yaml
→ внешний *.local.yaml
→ переменные окружения
→ аргументы команды
```

Последующие уровни имеют больший приоритет. Секретные значения допустимы только
на внешнем уровне или в переменных окружения. В Git хранятся схема настроек,
безопасные defaults и `.env.example` без значений секретов.

Каждый результат содержит fingerprint эффективной несекретной конфигурации.
Секреты исключаются из логов, ошибок, аудита, кэша и fingerprint.

## 5. Управление промптами

Канонический путь:

```text
prompts/<module>/<prompt_id>/vN.yaml
```

Минимальный контракт файла:

```yaml
id: qa.answer_with_evidence
version: 1
status: "draft"
purpose: "Сформировать ответ только по переданным Evidence"
inputs:
  - question
  - evidence_items
template: "<template is added with the module implementation>"
response_schema: "schema-v1.json"
tests:
  contract: "tests/contract/prompts/qa.answer_with_evidence/"
  quality_dataset: "tests/fixtures/evals/qa.answer_with_evidence-v1.jsonl"
```

Правила:

- файл промпта не содержит ключей, URL окружения и конкретной модели;
- параметры модели находятся в конфигурации провайдера;
- схема ответа версионируется отдельно;
- совместимое уточнение может увеличить patch-метаданные, изменение смысла
  создаёт `vN+1`;
- использованные prompt ID/version и model provider/version сохраняются
  в lineage;
- golden-набор не подменяет экспертную оценку; спорные изменения сравниваются
  на одном версионном eval-наборе.

## 6. Git-flow

1. Обновить `main` без локальных изменений.
2. Создать `codex/<краткое-имя>` или `claude/<краткое-имя>` по исполнителю.
3. Зафиксировать выбранный модуль в `docs/project-status.md`.
4. Реализовать модуль, тесты и документацию одним связным изменением.
5. Запустить локальные проверки.
6. Просмотреть `git diff` и staged diff, проверить отсутствие секретов.
7. Сделать атомарный коммит на русском языке.
8. Отправить ветку и создать PR в `main`.
9. Дождаться зелёного CI и независимого ревью.
10. После принятого решения слить PR и удалить ветку по правилам репозитория.

Запрещены прямые коммиты в `main`, смешивание несвязанных модулей, коммит кода
без тестов, force-push после начала ревью без предупреждения, секреты в истории
и «временное» отключение обязательной проверки.

### 6.1. Первый коммит нового репозитория

Для нового репозитория действует один точный bootstrap-сценарий:

1. План и окружение фиксируются локальным seed-коммитом в
   `codex/project-planning`.
2. Пользователь явно согласует этот snapshot как исходное состояние проекта.
3. Ответственное лицо переименовывает ветку в `main` и публикует её как первый
   `main`. Для единственного seed-коммита PR не создаётся.
4. Сразу после публикации `main` защищается; все следующие изменения идут от
   неё через `codex/*` и PR.

Агент не создаёт remote, не публикует seed и не меняет защиту без отдельного
запроса. До согласования bootstrap-ветка остаётся локальным кандидатом.

## 7. Pull request

PR должен отвечать на вопросы:

- какое требование и какой модуль закрыты;
- что изменено и что намеренно не изменено;
- какие контракты и данные затронуты;
- какие тесты и проверки выполнены;
- есть ли миграция, обратная совместимость и откат;
- какие риски и непроверенные предположения остались;
- обновлены ли статус, план, ADR и схемы.

Изменение готово к слиянию только при зелёном CI, отсутствии неразрешённых
замечаний и проверяемом результате из раздела «готово, когда».

## 8. Версионирование и данные

- Исходный документ неизменяем; исправление создаёт `DocumentVersion`.
  Единственное исключение — ручное удаление ошибочно загруженного документа
  преподавателем по ADR-011.
- Schema, DomainPackage, prompt, model, index и algorithm имеют версии.
- Миграции выполняются явно и имеют тест upgrade/rollback либо документированное
  ограничение восстановления.
- Пользовательские данные, индексы, кэши, журналы и экспорты не коммитятся.
- Демо-данные синтетические или имеют проверенную лицензию и происхождение.
- Кэш не считается резервной копией; backup/restore проверяется отдельно.

## 9. Документация и состояние

Архитектурная документация ведётся как код. Для MVP нужен уровень arc42
ESSENTIAL: цели, ограничения, C1/C2/C3, runtime, deployment, сквозные правила,
ADR, quality scenarios, риски и глоссарий.

Единый `docs/project-status.md` обновляется после каждого значимого этапа:
решения, выполненное, проверки, ограничения и следующий шаг. Дополнительные
«status-final-v2» документы запрещены.
