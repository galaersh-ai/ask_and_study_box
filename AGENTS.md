# Оперативные правила Knowledge Box

Этот файл обязателен для человека и агента, работающего с репозиторием.
Подробный регламент находится в `docs/development-rules.md`, действующие
требования — в `docs/requirements/README.md`, текущее состояние —
в `docs/project-status.md`.

## 1. Перед началом работы

1. Прочитать этот файл, реестр требований и раздел нужного модуля
   в `docs/development-plan.md`.
2. Проверить ветку, `git status` и незакоммиченные изменения. Чужие изменения
   не перезаписывать и не удалять.
3. Убедиться, что задача относится к MVP и не меняет согласованные границы.
   Иное сначала оформить как изменение требований или ADR.
4. Зафиксировать в `docs/project-status.md` выбранный модуль, входные условия
   и планируемые проверки.

Архивные документы не задают требования. Если код, план и действующий документ
расходятся, работу остановить до устранения противоречия.

## 2. Архитектурные инварианты

- MVP строится как модульный монолит с явными портами и адаптерами.
- `knowledge` не зависит от Web UI, CLI, MCP, конкретной базы данных,
  облачного SDK или конкретной LLM.
- Каждый модуль владеет своей моделью и публичным контрактом. Импорт внутренних
  реализаций другого модуля запрещён.
- Внешние сервисы, файловая система, часы, генераторы идентификаторов и модели
  доступны бизнес-логике только через порты.
- SQL и детали хранилища находятся только в адаптерах хранения.
- Сетевые вызовы находятся только в адаптерах провайдеров.
- Новый предметный пакет подключается без изменения ядра.
- Каждый существенный ответ связан с `Evidence`, координатами и версией
  источника. Неподтверждённое утверждение не выдаётся как факт.
- Результат хранит версии предметного пакета, промпта, модели, настроек и индекса.
- Ошибка одного документа не должна повреждать проект или весь пакет обработки.
- Повторный запуск на том же снимке, версиях и кэше должен быть воспроизводимым.
- Learning Studio, Assessment и юридическая логика не добавляются в ядро MVP.

Нарушение инварианта требует отдельного ADR. Молчаливое изменение запрещено.

## 3. Модуль и его тесты

Модуль считается готовым только одним изменением, в котором присутствуют:

1. публичный контракт и описанные зависимости;
2. реализация без обхода архитектурных границ;
3. модульные тесты;
4. контрактные тесты для каждого порта;
5. интеграционные тесты, если модуль работает с хранилищем или адаптером;
6. фикстуры без реальных секретов и сетевых запросов;
7. обновлённые план, статус и при необходимости ADR;
8. результаты обязательных проверок.

Unit-тесты зеркалируют модули из `src/knowledge_box/`. Contract-тесты
группируются по портам, integration-тесты — по адаптерам, acceptance-тесты —
по сценариям. Исправление дефекта начинается с регрессионного теста. Тесты
по умолчанию не ходят в сеть, не используют реальную LLM и не зависят
от порядка запуска.

## 4. Настройки, секреты и промпты

- Секреты передаются только через переменные окружения или внешний секрет-файл.
- `.env`, `*.local.yaml`, токены, пароли и ключи не коммитятся.
- `.env.example` содержит только имена переменных и безопасные примеры.
- Несекретные значения по умолчанию находятся в `config/`; числовые пороги,
  лимиты, модели и политики не зашиваются в код.
- Конфигурация валидируется при запуске. Неизвестный или отсутствующий
  обязательный параметр приводит к понятной ошибке.
- Тексты промптов запрещено хранить в Python, шаблонах интерфейса и настройках
  окружения. Они лежат только в `prompts/<module>/<prompt_id>/vN.yaml`.
- У промпта обязательны идентификатор, версия, статус, назначение, входы,
  шаблон, путь к схеме ответа и пути к contract/quality tests.
- Изменение смысла промпта создаёт новую версию. Использованная версия
  сохраняется вместе с результатом.

## 5. Git и pull request

- Работать только в ветке `codex/<краткое-имя-задачи>` от актуальной `main`.
  Исключение для нового репозитория описано в разделе 6.1 регламента.
- Прямая запись и слияние в `main` запрещены.
- Один коммит закрывает один модуль или одно связное изменение. Код и его тесты
  находятся в одном коммите.
- Сообщение коммита — краткое, на русском языке, в повелительном наклонении:
  `Добавить контракт загрузки документов`.
- Перед коммитом проверить staged diff и отсутствие секретов.
- Перед PR выполнить обязательные проверки и `git diff --check`.
- PR содержит цель, границы, ссылки на требования/ADR, перечень проверок, риски,
  способ отката и отдельный список того, что не выполнено.
- Значимое изменение проходит независимое ревью. Автор не сливает собственный
  PR без явного решения ответственного лица.
- Отметка о готовности ставится только после зелёных проверок и проверяемого
  результата, а не после написания кода.

## 6. Обязательные проверки

После PH-00 каноническими становятся команды:

```powershell
$env:UV_CACHE_DIR = ".uv-cache"
uv sync --frozen --group dev
uv run ruff format --check .
uv run ruff check .
uv run mypy src
uv run lint-imports
uv run pytest -q
$tracked = git ls-files
uv run detect-secrets-hook --baseline .secrets.baseline $tracked
git diff --check
```

Файл `.secrets.baseline` создаётся и аудируется на PH-00. Добавлять находку
в baseline без проверки запрещено; локально и в CI используется одна команда.

Для изменения документации до PH-00 обязательны проверка ссылок и структуры,
поиск секретов, `git diff --check` и ручная сверка с действующими требованиями.

## 7. Завершение задачи

Обновить `docs/project-status.md`: решения, выполненное, проверки, ограничения
и следующий шаг. Не создавать параллельный документ состояния. В итоге сообщить
проверяемый результат, выполненные проверки, оставшиеся ограничения и ссылку
на PR, если изменения опубликованы.
